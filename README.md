# Repository Analyzer

Многопоточный анализатор истории репозиториев с кодом на любом текстовом языке. Он восстанавливает граф коммитов, исследует diff, группирует изменения и формирует LLM-отчёт для выбранной роли: разработчика, аналитика, специалиста по безопасности, тимлида или руководителя. Отчёт включает изменения, риски, проверяемые задачи и источники; для Java сохраняется дополнительный разбор классов и методов через JavaParser.

![Главная страница Repository Analyzer](docs/images/main-page.png)

## Что происходит во время анализа

1. JGit клонирует репозиторий или обновляет его локальную копию.
2. История коммитов сохраняется в SQLite вместе с parent-связями.
3. До 10 worker-потоков в случайном порядке извлекают diff и изменённые файлы.
4. Для каждого текстового файла определяется язык по имени или shebang, неизвестные расширения также участвуют в анализе diff. JavaParser дополнительно выделяет пакеты, классы, методы и признаки ошибок разбора Java.
5. Из технических данных собирается компактный контекст, и LLM один раз разбирает каждый коммит в структурированный JSON: суть, категория, уровень риска, ключевые изменения, влияние на поведение, риски и проверки. Разбор не зависит от роли и переиспользуется всеми отчётами задачи. Небольшие коммиты отправляются пакетами, а слияния и обновления lock-файлов описываются без LLM.
6. Точные показатели считаются без LLM: период, авторы (псевдонимы с общим email склеиваются), активность, часто изменяемые файлы, распределение рисков и характер изменений.
7. По Git-дереву зафиксированного HEAD без LLM собирается состояние кода: описание из README, языки, манифесты, стек и зависимости, модули, число основных и тестовых файлов. Для Java/Kotlin дополнительно собираются текстовые признаки Spring: HTTP-контроллеры, Spring Security, отключённый CSRF, CORS `*`, открытый Actuator. В конфигурации отмечаются признаки секретов и закоммиченные `.env`; в сводке приводятся файл и имя параметра. Снимок переиспользуется между ролями только при совпадении репозитория и HEAD.
8. Для выбранной роли LLM возвращает структурированный JSON: выводы с ID источников, план действий и ограничения. Сервер сверяет точные числа с рассчитанными фактами, проверяет ссылки и пути файлов и только затем сохраняет и собирает текст отчёта. У каждой роли 3–5 разделов без пересечений; объём зависит от числа коммитов, каждый вывод ссылается на файл или коммит, находки помечаются уровнем (**[Подтверждено]**, **[Проверить]**, **[Высокий]**…), а PDF и Markdown показывают только нужные роли показатели.
9. Ответы кэшируются по хэшу prompt, временные ошибки inference-сервера повторяются автоматически, а неудачный коммит не останавливает отчёт.
   Если итоговый JSON не проходит проверку, система удаляет неверный ответ из кэша и один раз запрашивает новый на тех же полных источниках с причиной отказа. Повторный неверный ответ завершает отчёт ошибкой; проверки чисел, ссылок, путей и структуры сохраняются.
10. Результаты по коммитам поступают во frontend через SSE; при переподключении восстанавливается актуальное состояние. Готовый отчёт можно скачать в PDF или Markdown, выбранные задачи — в Markdown или JSON.

Анализ идемпотентен: завершённая работа не дублируется, после перезапуска её можно продолжить, а выполнение анализа и формирование отчёта можно остановить.

## Языки и границы анализа

Распознаются Java, Kotlin, JavaScript/TypeScript, Python, Go, Rust, C/C++, C#, F#, PHP, Ruby, Swift, Dart, Scala, Shell, PowerShell, SQL, Lua, R, Elixir, Erlang, Haskell, Clojure, Perl, Julia, Zig, Nim, Solidity, Terraform, шаблоны и конфигурация. Файлы без расширения определяются по shebang; неизвестный диалект получает пометку `Text (.ext)` и анализируется по текстовым изменениям. Расширение не является условием допуска diff к анализу.

Структурный AST-разбор доступен для Java. Для остальных языков это анализ текстового diff моделью, а не компиляция, проверка типов или полный аудит. Проверки защиты Spring не распространяются на другие фреймворки. Код и тесты проекта не выполняются, команды из манифестов не запускаются. Бинарные изменения могут быть перечислены в истории, но их содержимое не интерпретируется как код.

Существующие ограничения контекста сохранены: по умолчанию до 15 файлов, 1600 символов patch на файл и 10000 символов суммарно; признаки обрезки передаются модели. Снимок ограничен 30000 файлами, 4000 чтениями, 256 KiB на читаемый файл и 100 путями источников. Достижение лимитов явно указывается. «Любой язык» не означает одинаковую точность модели на любом диалекте; неизвестный синтаксис требует проверки выводов по источникам.

## Скорость и автоматические проверки

- Контекст пачки коммитов загружается тремя SQL-запросами на блок до 400 ID, вместо запросов для каждого файла, типа и метода. Содержимое контекста сверяется с прежней реализацией интеграционным тестом.
- Java-файлы одного коммита читаются через одно открытие Git. Повторный Java-разбор точного исходного текста переиспользует неизменяемый результат; кэш ограничен 64 элементами, большие исходники разбираются полностью без кэширования.
- Снимок проекта читается из неизменяемых Git-объектов и хранится в ограниченном кэше на 32 HEAD. Одновременные запросы одного снимка разделяют одну загрузку; ошибки не кэшируются.
- Разборы LLM сохраняются одной транзакцией на пачку. Поиск переиспользуемых результатов читает только ID, а факты периода загружают только нужные разборы.
- При смене роли, периода или старой версии frontend переиспользует граф, группы и теги текущей версии задачи. После обновления эти данные запрашиваются заново. История отчётов загружается через лёгкий `/api/analysis-tasks/{taskId}/report-summaries`, содержимое и источники — при открытии конкретного отчёта. Панели отчёта и истории загружаются при открытии анализа.

Модель, параллельность LLM, размеры пачек, лимиты контекста и длина ответов ради скорости не уменьшаются. Скорость самой модели остаётся отдельным ограничением. Измерения и методика: [docs/performance.md](docs/performance.md).

Все обязательные проверки одной командой (предварительно выполните `npm ci` в `frontend`):

```bash
sh scripts/check.sh
```

Проверка на установленной реальной модели, включая парное сравнение языкового режима и итоговые отчёты пяти ролей:

```bash
LLM_EVAL_MODEL=qwen3:8b sh scripts/evaluate-quality.sh
```

В парном сравнении нет допуска ухудшения: для каждого из 12 сценариев корректный JSON, категория, риск, упоминание источника и конкретные проверки не могут перейти из успешного состояния в неуспешное; ошибка уровня риска не может увеличиться. Промпты Java и остальных текстовых языков, а также прежние контексты проверяются на точное совпадение. Языки и манифесты добавлены в метаданные и итоговый снимок; вход коммитного анализа сохранён после отклонения ухудшавших проверки вариантов промпта. Результаты сохраняются в `target/llm-evaluation/multilanguage-report.{md,json}`. Это регрессионная защита на эталонном наборе, а не математическая гарантия качества на всех будущих репозиториях.

## Быстрый запуск

Понадобятся:

- JDK 21;
- Node.js и npm;
- Ollama с моделью `qwen3:8b` либо доступ к другому OpenAI-compatible API.

По умолчанию проект использует локальную Ollama. Подготовьте модель:

```bash
ollama pull qwen3:8b
ollama serve
```

Запустите backend из корня проекта:

```bash
./mvnw spring-boot:run
```

В другом окне терминала запустите frontend:

```bash
cd frontend
npm install
npm run dev
```

Откройте [http://localhost:5173](http://localhost:5173), вставьте HTTPS-ссылку на Git-репозиторий, укажите ветку, выберите роль и нажмите **«Начать анализ»**.

Для приватного репозитория раскройте в форме блок доступа и передайте personal access token с правом чтения. Токен используется только для `clone/fetch` и не сохраняется в SQLite.

## Порты и адреса

| Компонент | Адрес | Назначение |
|---|---|---|
| Frontend | [localhost:5173](http://localhost:5173) | Пользовательский интерфейс |
| Backend API | [localhost:8080](http://localhost:8080) | REST API и SSE |
| Swagger UI | [localhost:8080/swagger-ui/index.html](http://localhost:8080/swagger-ui/index.html) | Документация API |
| Health check | [localhost:8080/actuator/health](http://localhost:8080/actuator/health) | Состояние backend |
| Ollama | `localhost:11434` | Локальный LLM API |

SQLite не использует отдельный порт. База создаётся автоматически в `data/repository-analyzer.db`, а локальные копии репозиториев — в `data/repositories`.

## Подключение другой LLM

Настройки находятся в [`src/main/resources/application.properties`](src/main/resources/application.properties). Любой OpenAI-compatible сервер подключается заменой параметров:

```properties
repository-analyzer.llm.provider=openai-compatible
repository-analyzer.llm.provider-id=my-provider
repository-analyzer.llm.base-url=https://api.example.com
repository-analyzer.llm.chat-path=/v1/chat/completions
repository-analyzer.llm.model=my-model
repository-analyzer.llm.api-key=${LLM_API_KEY:}
```

Перед запуском передайте ключ через окружение и перезапустите backend:

```bash
export LLM_API_KEY=your-api-key
./mvnw spring-boot:run
```

Для локальной Ollama ключ не нужен. Лимиты параллельных запросов, объём контекста и длина ответов также настраиваются в `application.properties`.

## Период отчёта и экспорт

Рядом с выбором роли можно ограничить отчёт периодом: вся история, последний месяц, 3 или 6 месяцев, год, изменения после тега или между двумя тегами (например, отчёт за релиз `v1.1 → v1.2`). Период по дням отсчитывается от самого нового коммита ветки. Для каждой пары «роль + период» хранится отдельный отчёт, а разбор коммитов переиспользуется.

Готовый отчёт экспортируется в PDF или Markdown: файл можно скачать или скопировать текст в буфер и вставить в Confluence или Notion.

## Точность и краткость отчёта

Новые отчёты отделяют рассчитанные числовые факты от оценок модели и прикладывают к выводам доступные фрагменты diff и кода закреплённой версии Git. Покрытие и ограничения видны в отчёте и выгрузках. Дополнительная смысловая проверка моделью реализована, но выключена по умолчанию: локальная qwen3:8b не прошла контрольные примеры, поэтому исходный анализ сохраняется. Подробнее: [факты, источники и результаты проверки качества](docs/report-quality.md).

## Обновление анализа и проверка источников

После завершения нажмите **«Обновить анализ»**. Анализатор выполнит fetch, обработает только новые коммиты и переиспользует сохранённые diff, результаты JavaParser и разборы LLM. Если HEAD не изменился, версия анализа и готовый отчёт остаются прежними. После force push коммиты, исчезнувшие из ветки, исключаются из текущего графа, но сохраняются как источники старых отчётов.

У отчёта фиксируются версия анализа, HEAD, список коммитов, снимок состояния кода и итоговые показатели. Выбор **«Сохранённый отчёт»** позволяет открыть прежнюю версию для той же роли и периода. Для приватного репозитория при обновлении повторно укажите токен доступа.

Ссылки **C<ID>** рядом с выводами открывают сохранённый коммит и его diff с координатами строк; **F1** — точные показатели периода; **S1** — найденные признаки состояния кода и файлы из зафиксированного HEAD. Большие diff показываются частично с явной отметкой. Источник из другого отчёта запросить нельзя.

В **«Плане действий»** каждая задача содержит приоритет, основание, конкретные файлы, источники и наблюдаемый критерий проверки. Отметьте нужные задачи и выгрузите их в Markdown или JSON. Полный PDF и Markdown также включают план и источники.

Блок **«Проверка источников»** показывает выполненные автоматические проверки. Они выявляют неизвестные ID, неверные числа, выдуманные пути и некорректную структуру ответа; смысловую правильность интерпретации они не гарантируют. Невалидный ответ не публикуется и удаляется из кэша, чтобы повтор мог получить новую генерацию.

Миграция Flyway V9 обновляет существующую SQLite при запуске. Старые Markdown-отчёты сохраняются; новые интерактивные источники и задачи появятся после повторного формирования отчёта. Перед первым обновлением фиксируются входные данные старых отчётов.

## Контекст pull request'ов

Для репозиториев на GitHub и GitLab анализатор подтягивает описание pull/merge request, обсуждение и связанные задачи, к которым относится коммит. Это помогает модели понять, зачем сделано изменение. Результат кэшируется в базе.

Без токена GitHub разрешает около 60 запросов в час, поэтому для больших репозиториев задайте токен с правом чтения:

```bash
export GITHUB_TOKEN=ghp_...
export GITLAB_TOKEN=glpat-...   # для GitLab
export GITLAB_HOSTS=git.company.ru   # self-hosted GitLab, если хост не начинается с gitlab.
```

При исчерпании лимита загрузка PR приостанавливается до его сброса, а анализ продолжается без этого контекста.

## Безопасность

- Backend слушает только `127.0.0.1`. Для доступа по сети задайте `SERVER_ADDRESS=0.0.0.0` и обязательно `API_TOKEN`. Тот же токен укажите фронтенду в `VITE_API_TOKEN`.
- Клонируются только HTTPS-ссылки на публичные адреса. Корпоративный Git во внутренней сети разрешается через `ALLOW_PRIVATE_GIT_HOSTS=true`, а список разрешённых хостов задаётся через `ALLOWED_GIT_HOSTS=github.com,gitlab.company.ru`.
- Запросы к модели ограничены таймаутами (`repository-analyzer.llm.*-timeout-millis`). Остановка отчёта прерывает уже отправленные запросы.

## Проверка качества ответов модели

В `src/test/resources/evaluation/commit-insight-golden.json` лежит эталонный набор из 25 коммитов с ожидаемыми категорией и уровнем риска. После смены модели или промпта прогоните его на реальной LLM:

```bash
LLM_EVAL_MODEL=qwen3:8b ./mvnw test -Dgroups=llm-evaluation -Dllm.evaluation.excluded-groups=none -Dtest=CommitInsightQualityEvaluationTest -Dsurefire.failIfNoSpecifiedTests=false
```

Отчёт сохраняется в `target/llm-evaluation/report.md`: доля корректного JSON, точность категории, точность риска (строго и с допуском в один уровень) и список расхождений. Пороги задаются переменными `LLM_EVAL_MIN_JSON`, `LLM_EVAL_MIN_CATEGORY`, `LLM_EVAL_MIN_RISK`, `LLM_EVAL_MIN_RISK_WITHIN_ONE`, адрес сервера — `LLM_EVAL_BASE_URL`, ключ — `LLM_EVAL_API_KEY`. В обычной сборке этот тест не запускается.

Для итогового отчёта добавлен отдельный эталонный сценарий: удаление проверки отрицательной суммы, пять ролей, точные метрики, источники и конкретная задача с критерием проверки.

```bash
LLM_EVAL_MODEL=qwen3:8b ./mvnw test -Dgroups=llm-evaluation -Dllm.evaluation.excluded-groups=none -Dtest=SynthesisQualityEvaluationTest
```

Результаты сохраняются в `target/llm-evaluation/synthesis-report.md` и `.json`. Порог принятия задаётся через `LLM_EVAL_MIN_SYNTHESIS` (по умолчанию 1.0: пройти должны все пять ролей). Это небольшой регрессионный сценарий, который следует расширять примерами реальных проектов; он не является полной оценкой качества модели.

## Проверки разработки

```bash
./mvnw test
cd frontend
npm ci
npm test
npm run lint
npm run build
```

Backend-тесты покрывают обновление без новых коммитов, обработку только новых изменений, force push, сохранность прежнего отчёта, его источников и отклонение недостоверного синтеза. Frontend-тесты проверяют смену роли, периода и версии, запоздавшие ответы, восстановление SSE, остановку и повтор отчёта, просмотр diff и экспорт выбранных задач. Тесты на реальной LLM запускаются отдельно.
