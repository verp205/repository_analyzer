# Скорость и сохранность данных

Измерения относятся к локальному запуску 7 октября 2026 года. Их нельзя переносить на время генерации любого репозитория: при новых коммитах большую часть времени занимает модель и объём вывода.

## Загрузка контекста

Интеграционный тест `IncrementalAnalysisIntegrationTest.bulkContextIsIdenticalWithConstantQueryCount` создаёт временный Git-репозиторий и SQLite: два коммита, 12 Java-файлов с вложенными типами и методами, изменение одного файла во втором коммите. Прежний загрузчик сохранён только в тестах. Оба загрузчика читают одни данные в отдельных транзакциях, после чего сравниваются все поля контекста, включая порядок, patch, AST и ограничения.

| Показатель | Прежний загрузчик | Пакетный загрузчик |
|---|---:|---:|
| SQL-запросы | 59 | 3 |
| Время одного локального замера | 11 мс | 7 мс |
| Результат сравнения контекста | Полное совпадение | Полное совпадение |

Количество запросов сократилось на 94,9%. Это уменьшение обращений к базе, а не утверждение об ускорении полного отчёта на 94,9%. Время маленького примера чувствительно к прогреву JVM и состоянию системы; тест проверяет количество запросов и равенство результата, не нестабильный порог миллисекунд. Каждый последующий блок до 400 ID требует ещё три запроса.

Последний результат повторного запуска сохраняется в `target/performance/context.json`.

## Устранённая повторная работа

Java-файлы одного коммита читаются через один Git handle и один RevWalk. Кэш Java-анализа использует точный текст как ключ, хранит только неизменяемые DTO и подставляет правильный путь после переименования. Он не разделяет изменяемые экземпляры JavaParser. Исходники длиннее 256 Ki символов полностью разбираются без кэширования.

Снимок берётся из Git-объектов конкретного хэша отчёта, а не из потенциально изменённой рабочей копии. До 32 снимков хранятся в памяти, параллельные запросы одного хэша разделяют чтение, ошибка разрешает повторную попытку. Новый HEAD получает новый снимок; обращение к прежнему хэшу сохраняет прежнее содержимое. Отсутствующий Git-объект помечается недоступным и не подменяется текущей версией. Генерируемые каталоги пропускаются до входа в поддерево. Тест проверяет переиспользование, обновление и исключение незакоммиченных файлов.

При смене роли frontend повторно использует граф, группы и теги текущей ревизии: три запроса не повторяются. Отдельно проверяется повторная загрузка после обновления анализа. Список версий передаётся без текстов и источников отчётов; прежний полный API сохранён для совместимости.

Панели истории и отчёта загружаются отдельно. В локальной production-сборке основной JavaScript уменьшился с 573,71 до 395,96 kB (gzip: с 179,46 до 125,64 kB); это сокращение первоначальной загрузки, а не скорости генерации моделью. Браузерная проверка на временных API-данных подтверждает открытие Python-отчёта, языков, манифеста, исходного diff и прежней версии. После смены роли и версии количество запросов графа, групп и тегов осталось по одному.

## Качество

Модель, длина ответов, подробность JavaParser, размеры пачек и ограничения контекста ради ускорения не уменьшены. Сохранены повтор запросов при временных ошибках, валидация итоговых чисел, источников и задач, восстановление SSE и старые версии отчётов.

На исходном Java-наборе проверяется точное совпадение 25 одиночных и пяти пакетных промптов с сохранённой версией. Для 12 текстовых сценариев также проверяется совпадение одиночных промптов и общей пачки. Языковая метка остаётся метаданными; модель получает прежний полный текстовый diff и дополнительный AST только для Java. Варианты дополнительных инструкций, ухудшившие конкретность проверок, исключены. Контекст из базы отдельно сравнивается с прежним загрузчиком.

Языковой режим проверяется на Python, TypeScript, Go, Rust, C, C#, PHP, Ruby, Kotlin, Shell, файле без расширения и неизвестном диалекте. Для каждого сценария парное сравнение запрещает потерю ранее успешного JSON, категории, риска, источника или конкретной проверки, а также увеличение ошибки уровня риска. Итоговый синтез проверяется для пяти ролей. При известном HIGH-риске и доступном файле коммита пустой план не принимается: требуется задача с источником и конкретной проверкой. На первый отказ запускается одна повторная генерация со всеми исходными данными; второй отказ остаётся ошибкой, проверки не ослабляются.

Прогон обычных проверок:

```sh
sh scripts/check.sh
```

Прогон установленной реальной модели:

```sh
LLM_EVAL_MODEL=qwen3:8b sh scripts/evaluate-quality.sh
```

Результаты модели сохраняются в `target/llm-evaluation/`. Это проверка конкретных сценариев. Одинаковое качество на всех будущих языках и репозиториях нельзя доказать этим набором: смысловые выводы следует проверять по привязанным источникам и дополнять эталонными примерами проектов.

## Локальная проверка qwen3:8b

Итоговое парное сравнение 12 текстовых сценариев выполнено с прежними настройками: 700 выходных токенов, temperature=0, без дополнительного reasoning. Регрессий по проверяемым свойствам — 0.

| Проверка | Прежний вход | Текущий вход |
|---|---:|---:|
| JSON разобран | 12/12 | 12/12 |
| Ожидаемая категория | 11/12 | 11/12 |
| Точное совпадение ожидаемого риска | 2/12 | 2/12 |
| Упоминание исходного файла | 12/12 | 12/12 |
| Проверка связана с конкретным изменением | 12/12 | 12/12 |

Модель в этом наборе часто описывает опасное изменение, но занижает его уровень риска; в Shell-примере неверно трактует изменение кавычек. Эти ошибки присутствуют и в прежнем анализе. Отсутствие регрессий не означает безошибочную классификацию рисков. Числа в отчёте проверяются отдельно, смысл вывода — по diff.

В первоначальном прогоне итогового синтеза строгую проверку прошли 3 из 5 ролей: два ответа имели неверную структуру. После уточнения структуры и введения ограниченной повторной генерации прошли 4 из 5; у аналитика отсутствовала задача по известному HIGH-риску. После добавления проверки обязательной задачи повторный реальный прогон аналитика прошёл за два запроса. Сохранённые реальные ответы четырёх остальных ролей вместе с новым ответом аналитика повторно проверены текущим валидатором: 5/5. Это поэтапная проверка на одном фиксированном исходном примере, а не новый одновременный прогон пяти ролей и не доказательство истинности всех интерпретаций.

Артефакты: `multilanguage-report.{json,md}`, `baseline-synthesis-report.json`, `synthesis-report.json`, `synthesis-report-analyst.json` и `synthesis-replay-report.json` в `target/llm-evaluation/`. Для отдельного повторного прогона роли можно задать `LLM_EVAL_AUDIENCES=ANALYST`; общий скрипт по умолчанию проверяет все пять ролей и требует 100% принятия.

## Привязка цитат и дополнительная проверка

Новый формат отчёта по умолчанию прикладывает источники локально, без дополнительных запросов LLM. Он сохраняет первичные ролевые выводы, оговорки и оценки риска. Чтение фрагментов Git добавляет работу; отдельного замера его стоимости на больших репозиториях пока нет.

Экспериментальная повторная проверка моделью выключена по умолчанию после неуспешной проверки qwen3:8b. Общий скрипт оценки качества теперь также запускает `GroundedReportEvaluationTest`: этот новый этап не прошёл строгий порог на 12 сценариях. Приведённые выше результаты относятся к прежним отдельно указанным этапам. Подробности и ограничения: [качество отчётов](report-quality.md).
